## How this should inform A's proposed spatial/hybrid plan

This is **review guidance, not approval to change the live bot**. The current approved experiment is still the bounded v3.1 land observation/action contract described in [land-v3.md](land-v3.md); `strategy-review.html` is an unapproved draft. Spatial state, buildings, upgrades, new action types, and strategy prescriptions need Moritz's explicit discussion/approval before becoming model inputs or actions.

1. **Separate planner, judgment, and execution.** If a future design uses a Copilot LLM for event-triggered persistent planning and Jev for local decisions, specify what each produces and consumes. A plan is not an executable action. Let code generate legal candidate IDs, compute known costs/ratios and enforce freshness/legality; Jev selects or assesses only the bounded choices actually offered. Do not silently replace Jev's choice with a spatial heuristic.
2. **Pass only task-relevant, structured state.** An engine-derived tile/region/link layer can be built and tested in code, but any spatial summary supplied to Jev (or the planner) should be explicitly scoped and reviewed. Avoid feeding a giant map dump or generic system-message template by default. State exactly which source/derived fields each question needs and how identities map to current game entities.
3. **Decompose where the answer is independently useful.** A future building/upgrade workflow might need distinct judgments about tactical suitability, exposure or timing *if* those are genuinely semantic and permitted; known coverage, cost, candidate validity and legality belong in deterministic code. Keep the current wait/land-attack Choice as an observation baseline unless a change is approved. Do not convert the founder's decomposition advice into a hidden troop-reserve threshold or a forced sequence of actions.
4. **Define evaluation before prescribing fixes.** Preserve exact model state, candidate descriptions, model/version, output probabilities where available, emitted intent, and observed game outcome. Test candidate coverage and stale-choice handling separately from judgment quality. Use seeded game runs and retained failure cases to compare alternatives; distinguish a mock passing, a real Jev response, an intent emitted, and an actual game result. A v4 wilderness trace or an unverified v4.1 prompt adjustment is evidence to investigate, not proof of a causal fix.
5. **Specify uncertainty handling per consequence.** Confidence or score thresholds, if proposed later, require examples and an explicit fallback (wait, re-evaluate, human review, etc.) approved for that workflow. Low confidence is not a universal veto; high confidence is not a safety certificate. Note whether a question was actually used on the chosen branch. Multi-step model cascades are a possible future experiment, not something Almeida says must be shipped.

**Plan-review checklist for A:** Can a reader identify each proposed judgment's exact state, options/criteria, consumer in code, legal boundary, failure mode, evidence to evaluate it, and approval status? Are planner outputs kept separate from Jev's bounded local choices and real game outcomes? If not, the plan should call those out as open decisions rather than assume they are solved by prompting.
