# Tribe-focus v4.4: bounded Easy gameplay, no conquest yet

**Scope.** Real TypeSafe Jev decisions in one headed local OpenFront Solo Europe Compact match, Easy nations, 400 native tribes, five nations, random spawn, default starting gold. Jev was explicitly Started in opt-in Hybrid mode for **50 decisions** at ≥1-second request-start spacing; the Copilot planner was disabled (`COPILOT_GITHUB_TOKEN` not configured). The sidecar and in-game panel were observed, with no manual attacks or model-choice override. This is **not a completed match** and contains **no win result**.

**Evidence boundaries.** Ignored `logs/tribe-focus-easy-first50-browser.json.txt` contains the exact browser-observed raw decision inputs/responses, in-flight count and recent panel outcomes. The local `logs/decisions-2026-09-27T08-14-19.216Z.jsonl` includes these inference requests as part of the continuing sidecar session; the browser run is identified by its own 50-request sequence, not all rows of that JSONL. A sidecar response is a model choice, panel text “land attack intent sent” is a normal intent, and changing tiles/target life are game observations. A normal intent is not by itself a confirmed conquest.

**Diagnosis.** The *categorical* correction worked in this local trace: no new player/nation front while the focused tribe survived, and no 10–50% tribe cap violation. The *economic objective* did not: repeated 10% sends and waits failed to eliminate that growing native tribe over the observed window, so the desired conquest gold was not earned. The tribe’s territorial rise is observed, **not claimed to have been caused by our attacks**; it can expand into other wilderness. This is one stochastic game, not proof that 10% always fails or 20% always succeeds. The browser trace does not include exact GameView ticks in its raw land requests, so an exact `elapsed_ticks` value cannot be reconstructed from these historical requests.

**Next measured change.** A code-owned, source-labelled focus history now records the true GameView reference tick/tribe tiles when an intent is **emitted**, the count of such intents (not game-accepted conquests), latest 10%/20% fraction, and later same-target territory delta. A new Jev instruction will let the model compare **wait, 10% and 20%** when repeated small sends have not finished, while preserving Moritz’s absolute ≤20% tribe ceiling. This is an evaluation hypothesis, not an undisclosed hard-coded escalation. A separate [matched native-TribeExecution study](tribe-gold-and-nation-hostility.md) shows 20% follow-ups can finish cases that repeated 10% did not, but establishes no universal kill threshold. Run another bounded Easy match with the updated policy, explicitly record model choice → intent → target death/ConquestEvent → gold, and only then advance difficulty.
