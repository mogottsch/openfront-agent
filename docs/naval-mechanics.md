# Onion island: transport-ship mechanics (read-only research)

This is an **engine mechanics experiment**, not a new bot action or a Jev result. It uses OpenFront checkout `bb8af015b515b3b717bd4d901074c5f4c16641cb` and the real Onion map. No TypeSafe/Copilot request is made, and no upstream file is changed. The current playable bot has land and opt-in City action paths, but **no naval observation or action** yet. Moritz has since delegated autonomous local development toward beating Impossible native bots; an Onion full match proved the starting island cannot be escaped through land actions. A staged, tested naval expansion is within that local-only mandate; it is not deployed or authorized for multiplayer.

## Reproduce the bounded headless crossing

From `openfront-agent`, with the sibling OpenFront checkout installed:

```sh
../OpenFrontIO/node_modules/.bin/tsx --tsconfig ../OpenFrontIO/tsconfig.json scripts/analyze-naval.mts
```

The script writes ignored `logs/naval-mechanics.json`. It creates a fresh production Onion map, one human at `(400,280)`, no opponents, no model calls, and runs real `Config`/`GameRunner`/`Executor`. Normal stamped 20%-wilderness attack turns grow the starting island. Once it owns all 6,505 tiles, it submits **one normal `boat` intent** to the unowned outer-ring shore `(423,276)` and advances at most 500 ticks to land. This is an isolated route/intent test, **not** a win or a comparison against Impossible nations.

Two repeated runs produced byte-identical JSON. At the initial spawn (game tick 2), the human owned 52 tiles, **zero shoreline tiles**, and `canBuild(TransportShip, destination)` returned false. At **live tick 10** (game tick 12, about one simulated second after spawn), it had 134 tiles, seven owned shoreline tiles, **zero ports**, and the first sampled legal source was `(404,276)`. First eligibility is sampled every ten ticks; it may have arisen earlier between samples. After 45 land sends the 6,505-tile island was complete by game tick 449. A boat was buildable from `(404,276)` to the resolved landing shore `(423,276)` across the same water component. The native water path contained 20 tile refs; Manhattan shore-to-shore distance was 19.

## Adapter → worker → stamped boat → engine landing (explicit mock Choice)

A separate, network-free integration check exercises the **browser naval adapter itself**, not just direct core boat execution:

```sh
../OpenFrontIO/node_modules/.bin/tsx --tsconfig ../OpenFrontIO/tsconfig.json scripts/verify-naval-adapter.mts
```

It expands the same production Onion starting island to 6,505 tiles in the real `GameRunner`, then invokes `createNavalAdapter(...).propose()` exactly once. Its GameView-compatible read facade delegates map/tick/immunity/fleet/ownership methods to the **actual core Game and Player**. The one missing `PlayerView.buildables(tile,[TransportShip])` method delegates to the real worker-facing `runner.playerBuildables(playerID,x,y,[TransportShip])`; it does **not** invent a canBuild/source result. A fixed **explicit mock Choice** selects the first offered wilderness candidate by its opaque ID at 10%, then calls `adapter.canExecute(id,0.1)` and `adapter.execute(id,0.1)` without advancing the tick. The injected callback queues only the adapter's exact destination tile and internal troop amount into the next normal stamped `boat` turn. There is no TypeSafe/Copilot request and no live Jev choice.

On checkout `bb8af015b`, the real adapter offered **11/11** eligible shores, all worker-checked, with zero omissions. The mock chose ID `naval-adapter-onion-001/onion@449#1:boat1`; its worker source was `(291,157)`, destination `(179,0)`, and the adapter emitted **961 internal troops** (10% of 9,614 available). The next engine tick created a transport with exactly that source, destination, and payload. After **269** more ticks, the boat had landed on and owned the wilderness shore; one further tick showed the queued normal land attack with 945 surviving internal troops. The output `logs/naval-adapter-engine.json` is ignored, and two runs were byte-identical. This is a distinct, longer candidate than the direct-core `(423,276)` 20-tick test above. It verifies this *sampled wilderness path* through adapter candidate ID → real worker source → intent → observed landing, **not** target ranking quality, enemy immunity handling, durability under AI opposition, or a game win. Facade parity is limited to the methods actually exercised here; native `PlayerView` still runs in the browser for real gameplay.

## Engine contract and actual constraints

1. **Intent shape:** `src/core/Schemas.ts:630-635` defines `boat` with a nonnegative integer **destination tile ref** `dst` and nonnegative numeric `troops`. `src/core/execution/ExecutionManager.ts:83-84` maps the stamped intent to `TransportShipExecution(player, dst, troops)`. The sender's `clientID` is stamped by the local/server turn pipeline; the intent does **not** provide a target player ID, source shore, route, or percentage.
2. **Landing selection and water connectivity:** `src/core/game/TransportShipUtils.ts:5-50` resolves the *owner of the clicked destination* and asks `SpatialQuery.closestReachableShore`. `src/core/pathfinding/spatial/SpatialQuery.ts:126-166` searches up to **50 Manhattan tiles from the clicked tile** for land shore of that owner on a water component touching the attacker's owned shoreline. `closestShoreByWater` at `SpatialQuery.ts:187-216` then selects an owned source shore with a real water route to that landing. Thus a click may resolve to a *different* nearby shore tile; a disconnected inland lake is not a usable route. OpenFront's own regression `tests/core/game/TransportShipUtils.test.ts:48-64` tests avoiding an unreachable lake-facing shore.
3. **Ownership, legality, and fleet:** `TransportShipUtils.ts:5-30` rejects own-target clicks and players protected by `canAttackPlayer`, checks the unit cap, and requires a reachable source. `src/core/game/PlayerImpl.ts:1425-1440,1550-1586` checks unit disabled/alive/gold and delegates to this transport rule. `src/core/configuration/Config.ts:839-844` limits active transports to **three** (zero if transport disabled). Transport costs **0 gold** (`Config.ts:561-565`). There is **no port requirement** in these buildability checks; the actual early, port-free route above confirms it. A port may matter for other ship/economy mechanics, not this transport launch.
4. **Troops, route, and landing:** `src/core/execution/TransportShipExecution.ts:37-140` rechecks the destination ref, actual target, cap, legality, target shore, and source at execution time. Requested troops are capped to current available troops (`:103-107`); `PlayerImpl.ts:1367-1391` removes the boat's troop payload when building its unit. The boat moves one water-path step per tick (`TransportShipExecution.ts:25,172-185,238-286`); on arrival it takes the landing tile and queues a normal `AttackExecution` with its remaining troop payload. If the route later fails it refunds surviving boat troops (`:287-299`); the click and a successful buildability precheck do **not** guarantee eventual landing.
5. **Distance is not one global cap:** The core's 50-tile value limits *clicked ref → candidate landing shore*, not voyage length. Ordinary-click **auto-boat UI** separately checks land target and `euclideanDistSquared(clicked, source) < 100²` in `src/client/ClientGameRunner.ts:1535-1548`. Explicit boat-under-cursor uses `buildables(tile, [TransportShip])` without that auto-click proximity check (`ClientGameRunner.ts:1347-1368`). The normal intent still needs a valid reachable water route; do not turn the UI's 100 into an engine legality rule.

## Proposed bot contract — not yet deployed

A future naval candidate would minimally need an **engine tile ref for a legal destination**, its current target ownership/relationship/immunity, a current worker/core `canBuild(TransportShip, dst)` source result, available troops, active boat count/cap, and a water-reachability/path-distance summary if the model should compare voyages. At execution, code must recheck the destination owner, source, route, unit cap, legality and troop amount against the current game state; only a selected and still-legal candidate would produce `{type:"boat", dst, troops}`. The v4.2 **land-only** observation has no destination tile or water-component/boat state. A separate opt-in hybrid naval adapter now has unit tests and the one headless mock-choice check above, but there is no successful live model-chosen naval outcome while the external API is returning HTTP 529. The headless scripts prove mechanics and sampled Onion crossings, **not** that any generated candidate or chosen percentage wins a match. A model-facing naval option still needs bounded worker-checked target candidates, the tribe ≤20% hard cap, reserve-preserving sizing, active fleet state, stale-response rejection, a normal bridge intent and a bounded real-game smoke before claiming live success. Do not infer a boat route solely from the geometric water map.
