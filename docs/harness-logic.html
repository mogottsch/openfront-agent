The strategy we are implementing

1 · Conquest gold, not endless pokes

Before a focus exists, compare a viable weak or contested tribe with more wilderness expansion. A tribe payoff requires finishing its conquest; a partial attack or rising wallet does not prove that payoff.

Current emphasis is tribe gold; older “always wilderness first” descriptions are historical.

2 · Finish the chosen tribe

When Jev sends an attack at a tribe, remember that target until the game confirms it is dead. Wait if the existing push looks sufficient; reinforce the same target when safe.

An exhausted attack or missing border does not mean conquest. If the border is lost, wilderness can be offered to reconnect.

3 · Preserve the home army

Jev chooses wait, 10% or 20% against a tribe. Repeated ineffective 10% sends should be compared with 20% and regrowth—not blindly repeated or automatically escalated.

Incoming danger includes attackers’ reserves plus forces already heading toward us. No fixed 30% reserve rule.

Nations come later: the code withholds nation targets while unallied bordering tribes remain. Without tribe focus or existing tribe attacks, this rule does not block human targets. Afterward the prompt asks Jev to attack a nation only when a complete conquest is credible, preferably one send. That is a judgment—not a proven kill predictor; optional building counts do not reveal placement, terrain, range or future resistance.

Hard harness rules vs. Jev judgments

Code enforces

  • Tribes: at most 20%; other land / boat targets: offered 10–50% increments.
  • Persistent focus and disclosed removal of unrelated land / boat targets before inference.
  • Friendly, immune, unaffordable or stale options cannot execute.
  • One request at a time; at least one second between request starts.
  • Start / Stop, bounded request budget, no hidden retry on service failure.

Jev decides

  • Initial target from the offered menu.
  • Wait, reinforce, and troop amount.
  • Immediate action family in Hybrid: land, City, boat, Defense Post or wait.
  • Which offered building site / boat coast is worthwhile.
  • Whether a nation conquest is credible from the supplied facts.

Important distinction

There is a user-authored strategy gate in code now. The harness is not wholly strategy-neutral.

But it does not overwrite Jev’s returned choice with a preferred move or secretly resize it. Builds and waiting remain available during tribe focus; the no-new-front rule applies to attack targets.

Normal spatial scans are scheduled about every 15 seconds, not on each one-second decision. Cheap affordability / owned-shore checks avoid impossible scans; missing opportunities can recheck within five seconds. Old proposals expire; menu availability can therefore change between decisions. Omitted candidates are disclosed, not claimed optimal.

One decision, end to end

  1. Only an explicitly Started local run can request a decision. Take fresh game facts and verify the focused tribe’s identity and life.
  2. Build legal candidates, apply the disclosed priority gate, and project bounded facts. If only wait is available, poll locally without spending a model request.
  3. The Node sidecar keeps credentials server-side. One TypeSafe request asks typed Choice questions. In Hybrid, independent questions are answered together; only the selected branch’s answer is used.
  4. Validate returned IDs / probabilities, the game and proposal identity, run generation and freshness. Recheck the selected action with the real worker. Discard changed / invalid choices.
  5. Send a normal game intent. Record emitted-send history and observe later game changes; emission is not acceptance, conquest, gold transfer, construction completion or landing. The tribe progress reference is the decision’s observation before inference; elapsed time is since that observation, not since emission or acceptance.
External requests and planner boundary

Browser → local sidecar → TypeSafe POST /v1/systemone with model, projected state and typed questions. Browser Start tokens are local authorization, not model credentials. No model-generated code or client tool calls execute.

Optional server-owned Copilot planning can suggest an objective. It does not directly choose or execute game intents. Its real availability is shown above; no validated Copilot-guided play has been demonstrated in the recorded evidence. Successful use requires explicit server-side authorization.

What we know vs. what still needs proof

New observed milestone: in a bounded 90-decision real-Jev Easy run, three 20% attacks finished one native tribe and the engine confirmed its 7,350-gold conquest payout. Focus cleared only after confirmed death. This was land-only, headless, with engine ticks paused during inference; it stopped at the call cap, not a match win.

The earlier Easy browser run kept its target but did not finish it. The new run differs in setup and timing, so it is not a controlled proof that the prompt change caused improvement. The earlier complete Impossible land-only match still lost after filling its starting island. Excessive later waiting and the wider hybrid strategy remain open evaluation questions.

A network-free native-AI audit observed an enemy City move from constructing to complete and checked the inventory accessors. That is not Chrome gameplay, a City built by us, or a Jev building decision. Real model use of the new inventory remains unverified.

Mechanics tests, a model decision, an emitted intent and an observed outcome are separate evidence. A mock-built City / Post or mock-chosen boat landing is not Jev gameplay. The next useful feedback is whether real model play can repeat that tribe finish in browser play, avoid excessive waiting, use its building / boat choices and complete winning matches.
